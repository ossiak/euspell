# Publishing the white paper — status

How *Spelling Reform: An Engineering Approach* gets from `euspell_paper.odt` onto
euspell.org, what is published right now, and what still has to go into it.

Two kinds of tracking, deliberately separate:

- **Is the deployed copy current?** — machine-checked. `paper.published.json`
  records the hash of the ODT that was published, and `npm run paper:check`
  compares it against the source. Don't hand-maintain that; it lies the moment
  you do.
- **Is the paper finished?** — this document. The pending list below is
  editorial, and nothing can check it for you.

**Last updated:** 7 August 2026

## Published now

| | |
| --- | --- |
| Source | `euspell_paper.odt` (repo root) |
| Last published | 7 August 2026, from the 7 Aug 08:58 draft |
| PDF | `euspell.org/paper/euspell_paper.pdf` — 26 pp, **the authoritative form** |
| Paper page | `euspell.org/paper/` — previews the PDF inline and offers the download |
| Plain-text edition | `euspell.org/paper/text.html` — the LibreOffice HTML export, kept because the PDF cannot reflow |
| Linked from | the **Reference** column of `euspell.org/docs`, and the download line under the byline |

**The PDF is the form readers get.** The HTML export reflows the paper into the
word processor's layout, which loses the typesetting the paper is partly making
its argument with, so `/paper/` is now a real Next route
(`euspell_website/src/app/paper/page.tsx`) that previews the PDF in an `<object>`
and puts **Download the PDF** at the top. The HTML stays as a secondary text
edition rather than the front door.

That is also why the export is written as `text.html` and **not** `index.html`:
`/paper/` is generated by the route, and a `public/paper/index.html` would
collide with it in the static export.

### What the text edition is for — and isn't

**It is for reflow.** The PDF is a fixed 26-page Letter layout, so on a phone it
is constant pinching and scrolling, and no PDF can reflow. That is the whole
case for keeping it.

**It is not an accessibility fallback**, which is what it looks like and is easy
to write down without checking. LibreOffice exports a *tagged* PDF, so the two
editions measure like this:

| | `text.html` | `euspell_paper.pdf` |
| --- | --- | --- |
| Headings | 8 `<h2>` | 8 `/H2` — the same eight |
| Language declared | none — bare `<html>` | `/Lang(en-US)` |
| Figure alt text | 0 of 6 | 0 of 6 |
| Table headers | 16 `<th>`, none with `scope` | tagged `/Table` |
| Body | 1072 `<p>`, 2264 `<font>` | tagged structure |

Both take their structure from the same ODT paragraph styles, so the HTML adds
no headings — and it drops the language declaration, which is what tells a
screen reader to read a paper about English in an English voice. On that metric
the HTML is the weaker of the two.

Worth knowing separately: for *this* paper, speech output is degraded whatever
the format. The argument runs through before/after tables setting `through`
against `thruh` — 12 tables, 795 cells — and read aloud that pair either sounds
identical or differs misleadingly. Braille conveys it correctly, character by
character, and reads the tagged PDF as happily as the HTML. So neither format
choice rescues the comparison; only sight or braille does.

Not yet deployed: the site build carrying `/paper/` has been produced but the
`out/` upload to Hostinger has not been done. See
[launch-readiness.md](launch-readiness.md) for why the paper is being held back
in the first place — the repositories it promises GPL-3 source at are still
private, and that ordering has not changed.

## Republishing

One command, from `euspell_website/`:

```bash
npm run paper:publish   # re-export HTML + PDF from the ODT, re-apply the markers
npm run build           # checks the paper is current, then builds out/
```

Then upload `out/` to Hostinger.

**Never export the paper by hand.** LibreOffice's HTML export overwrites the
whole page and knows nothing about the three things the published copy needs:

1. `data-euspell="off"` on `<body>` — the extension's opt-out, so the paper
   stays in traditional spelling. Without it the before/after tables are
   double-transformed and the argument the paper is making disappears.
2. A `<title>` and a viewport meta, neither of which the export supplies.
3. The `Download the PDF` link, carrying `?euspell=off` so the PDF isn't pulled
   into the extension's reforming viewer either.

The paper page carries the same `?euspell=off` on every link that can reach the
PDF as a navigation, and it matters more there than on the download link: the
service worker's `onHeadersReceived` deliberately catches PDFs in a first-level
iframe — "the shape a site uses to preview a PDF" — and redirects the **whole
tab** into the viewer, not just the frame. Without the query, a reader with the
extension installed would be thrown off the paper page into a reformed copy.

`scripts/publish-paper.mjs` re-applies all three and aborts if any of them fails
to land. Both markers are explained in [opting-out.md](opting-out.md).

## The staleness check

`scripts/check-paper.mjs` runs automatically as `prebuild`, so every `npm run
build` reports one of:

```text
  ✔ paper current (published 3 Aug 2026, 15:21)
```

```text
  ⚠  PAPER OUT OF DATE
       source:    euspell_paper.odt  (5 Aug 2026, 11:02)
       published: public/paper/      (3 Aug 2026, 15:21, 2 days ago)
       the site would deploy the older draft.
       run `npm run paper:publish` to regenerate the HTML and PDF.
```

It warns rather than fails — a stale paper shouldn't block a build done for an
unrelated reason. `npm run paper:check --strict` exits non-zero instead, if that
is ever wanted in CI.

The check compares a SHA-256 of the ODT, not its timestamp, so merely opening
and re-saving the paper doesn't raise a false alarm.

## Pending before the next publish

- [ ] **Set the document title in the ODT** — File ▸ Properties ▸ Description ▸
      Title = `Spelling Reform: An Engineering Approach`. The ODT has no
      `dc:title`, so the exported PDF has no document-level `/Title` and a
      browser tab shows `euspell_paper.pdf` instead of the paper's name. The
      HTML title is injected by the publish script and is already correct; the
      PDF's cannot be — it comes from document properties, and the publish
      script warns after every export until it is set. **This matters more now
      that the PDF is the form readers open**: it is what the tab says for
      anyone using *Open in a new tab* from the paper page.
- [ ] **Alt text on the six figures** — set in the ODT (right-click the image ▸
      Properties ▸ Alt Text), the same shape of fix as the document title above:
      only the source can supply it, and it then flows into the tagged PDF and
      the HTML export together on the next publish. Both editions currently
      carry `/Alt` on 0 of 6 figures, which is the one real accessibility gap in
      the paper — everything else is already tagged. `pdfHasDocumentTitle()` in
      the publish script is the model if this is ever worth warning about too.
- [x] **Extension install instructions** — unblocked. The Chrome Web Store
      listing went live on 17 August and serves every Chromium browser, and the
      Safari build is a notarized DMG. Firefox is Mozilla-signed and published
      with the releases. The paper
      no longer prints steps at all: Appendix A points readers online instead,
      so a store URL changing does not strand a printed edition. See
      [paper-appendix-a.md](paper-appendix-a.md) and [signing.md](signing.md).
- [x] **Eupub install instructions** — unblocked. `ossiak/eupub` is public and
      v0.3.1 ships four signed assets per release (Authenticode installer,
      notarized DMG, AppImage, signed APK), so every platform has a download
      link that works for a reader. iOS is on the App Store as of 20 August.
- [x] **Re-check the GPL-3 source URLs** the paper prints. Both repositories are
      public and return 200: `ossiak/euspell` since 15 August, `ossiak/eupub`
      since 16 August.
- [ ] **Re-export after any figure change.** LibreOffice names extracted images
      by content hash, so an edited figure lands under a new filename — the
      publish script clears `public/paper/` first, which is what keeps orphaned
      PNGs from accumulating.

Once install instructions go in, the paper stops being a purely descriptive
document and starts making promises a reader will immediately test. Worth a pass
over it with that in mind before publishing that draft.
